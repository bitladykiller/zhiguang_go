# 设计约定与模式

> 本篇不对应单一代码域——它记录整个项目遵循的**设计约定**，以及每条约定背后真实发生过的反例。
> 新增代码应当遵守这些约定；面试中它们也正是「你如何做设计决策」的第一手素材。

每一节的结构都是：**约定 → 反例（本项目真实踩过的坑）→ 现在的做法**。

---

## 1. 接口定义在消费侧，按需声明

**约定**：模块依赖外部能力时，在**自己包内**声明一个只含所需方法的窄接口；绝不别名或引用生产者侧的完整接口。

**反例**：`knowpost` 曾写下 `type CounterClient = counter.CounterServiceInterface`——把生产者的 13 方法胖接口整个别名过来，而详情读取只用其中 2 个。代价立刻体现在测试上：为了测一个 enrich 函数，桩对象被迫实现全部 13 个方法、60 多行；而且 counter 任何签名演进都会波及所有别名方（本次 GetLikers 游标改造时，search 的同款别名就触发过一次连锁编译失败）。

**现在**：`knowpost/detail_service.go` 的 `detailEngagement`（2 方法）、`feed_service.go` 的 `feedEngagement`（3 方法）、`search/service.go` 的 `SearchCounterClient`（3 方法）、`relation` 的 `UserCounterUpdater`（1 方法）。依赖面即真实使用面，桩缩到几行。

> Go 谚语版本："Accept interfaces, return structs; define interfaces at the point of use."

## 2. 共享视图进缓存，用户态读后叠加——用结构保证，不靠纪律

**约定**：任何键中不含用户 ID 的缓存，内容中不得出现用户维度字段（liked/faved 等）。该不变量由 `cache.Tiered` **结构性**保证：它在 `Get` 返回前就完成全部缓存写入，缓存里只可能出现 Loader 的原始产物；调用方拿到返回值后再叠加用户态，怎么改都污染不了缓存。

**反例**：公共 Feed 曾把「已叠加某用户 Liked/Faved 的响应」写进全体用户共享的 L1 整页缓存——后续命中该键的其他用户读到了别人的点赞状态（跨用户串号）。根因是同一套「L1→L2→锁→回源→回填」的舞步在三处手写，其中一处 enrich 与回填的顺序写反了。**复制粘贴的模式没有结构可言，正确性只能逐处人工核对。**

**现在**：详情与「我的已发布」跑在 `cache.Tiered[T]` 上（`internal/cache/tiered.go`），公共 Feed 的碎片组装虽保留自定义路径，但同样遵守「组装返回公共视图、`withUserState` 统一叠加」的分层。

## 3. 每个模块一份键注册表

**约定**：模块占用的 Redis 键 schema 集中在一个 `keys.go`（或等价文件）里定义，配一张「键 → 类型 → 用途」总表；业务代码不得出现裸的 `fmt.Sprintf` 键拼接。**键属于谁，Lua/读/写/失效就都从谁那里取。**

**反例一**：`feed:item:` 前缀曾散落在 3 个文件里各自拼接。**反例二**（更隐蔽）：relation 为了原子性把 `cnt:user:{id}` 的格式复制进了自己的 Lua——那是 counter 的存储布局，布局演进时必然漏改。解法不是放弃原子性，而是把整段 Lua 连同键一起放回 counter（`ApplyFollowDeltaOnce`），relation 只依赖窄接口。

**现在**：`knowpost/keys.go`、`counter/likers.go` 键区、`fanout/keys.go`。

## 4. 默认值单源：零值 + 节级 ApplyDefaults

**约定**：每个配置节的默认值只在 `pkg/config` 的**节级** `ApplyDefaults()` 方法里出现一次。业务侧的零配置回退（单测不传 cfg）走同一条代码路径：`var s Section; s.ApplyDefaults()`。

**反例**：`feedCacheTTLValues` 曾内置一张 15 个数字的回退表，注释写着「与 ApplyDefaults **一致**的历史默认值」——一致性靠人肉注释维持，就是等着漂移。

**现在**：`config.KnowPostDetailCacheConfig.ApplyDefaults()` / `KnowPostFeedCacheConfig.ApplyDefaults()`，全局装配与 `detailCacheConfig()/feedCacheConfig()` 回退共用；`TestDetailCacheTTLValues_DefaultsMatchConfigSection` 把「同源」锁进测试。

## 5. 至少一次投递下的幂等协议：可重放的先做，不可重放的与落标同一原子单元

**约定**：消费端处理顺序必须是——幂等操作（可安全重放）在前，失败即返回错误交给重投；**不幂等**操作与去重标记合进同一段 Lua/事务，保证「标记与副作用要么都发生、要么都不发生」。

**反例**：relation 消费端曾经「SetNX 落标 → ZSet → HIncrBy 计数」。标记先落，后面任一步失败，重投命中标记被当成已处理跳过——那次关注在计数里**永久少一**。

**现在**：`applyZSets`（幂等）先行；`counter.ApplyFollowDeltaOnce` 单段 Lua 完成「SETNX + 双向 HINCRBY」。回归测试 `TestProcess_RetryAfterCountFailureIsNotLost` 直接演练「计数失败→重投→最终计到」。

## 6. 游标分页统一约定：复合双键、不透明、包含式区间 + 应用侧跳过

**约定**：动态列表一律游标分页，不用 offset（翻页期间的插入会跳条/重条）。游标格式统一为**自描述复合串**（`t:{score}:{id}`、`u:{id}`），对客户端不透明；查询用**包含式** score 上界，并列成员由应用侧按 (score, member) 精确跳过。

**反例一**：relation 的游标只有 score 且用排除式区间 `("` ——毫秒并列且恰在页边界时，并列成员被整页吞掉。**反例二**：`HomeTimelinePostIDs` 曾在边界上把 score 丢弃只返回 ID，上层被迫做 offset 分页——需要的信息在抽象边界上被提前扔掉了。

**现在**：likers（`t:/u:` 前缀区分时间序与回退序）、首页信息流（`t:{score}:{postID}`）同一约定；并列跨页有专门回归测试。

## 7. 让每种查询各有胜任的索引——存储选型不得反向决定 API 语义

**约定**：真值结构按写入/判定效率选型；某种查询语义若真值结构无法胜任，为它建**专用索引**并与真值在同一原子单元内维护，而不是让 API 迁就存储。

**反例**：点赞真值是 Bitmap（O(1) 判定、极省内存），但 Bitmap 只能按 userID 枚举成员——于是「谁赞了我」列表长期按 userID 排序，而产品语义几乎总是「最近点赞的在前」。这是典型的本末倒置。

**现在**：toggle 的 Lua 同时维护 Bitmap（真值）与 `likers:{...}` ZSet（score=时间，时间序索引）；列表走 ZSet，索引缺失（历史数据）回退位图扫描。

## 8. 必需依赖与可选降级要区分对待

**约定**：「nil 即静默跳过」只允许用于**真可选**能力（LLM 未配→503、hotKey 未配→不延长 TTL）。会造成**静默正确性丢失**的依赖（如写后缓存失效器）不允许静默跳过——要么构造期拒绝，要么至少在跳过时高声告警。

**反例**：`feedCache == nil` 时写路径静默不失效 Feed 缓存——装配漏了一根线，表现是「缓存永不更新」，没有任何日志指向根因。

**现在**：bootstrap 在构造期就把 feedSvc 作为构造参数传入写服务（不再是 setter）；仍然保留的 setter（`SetHomeTimelineReader`/`SetFanoutHooks`/`SetRunnerReporter`）都是构造顺序环所迫，且逐一注释了原因——setter 注入应当是显式标注的例外，而非默认习惯。

## 9. 事件自描述；动作类消费者与投影类消费者的位点策略不同

**约定**：outbox 事件载荷应携带消费者所需的全部字段（`creator_id`、`published_at`、`visible`……），消费者不回查数据库。**投影类**消费者（搜索、关系）从最早位点回放以重建投影；**动作类**消费者（扩散：把帖子推进收件箱）从 Latest 起步——回放历史等于把陈年旧帖当新内容重新分发。

**反例**：扩散消费者曾对缺 `published_at` 的历史事件用「当前时间」兜底；叠加新消费者组默认从最早位点回放，上线一刻会把全部旧帖以「现在」的时间戳刷满所有人的收件箱。

**现在**：`NewKafkaReaderWithGroupFromLatest` + 缺时间戳事件直接跳过。

## 10. 其余零散约定

| 约定 | 出处 |
|---|---|
| 通用缓存工具统一归属 `internal/cache`（PrefixCache/HotKey/Bloom/Tiered/Versions） | 曾有 PrefixCache 落在 knowpost |
| 跨模块共享类型必须有两个以上真实使用方，否则归还唯一使用方 | `model.FeedItem` 号称共享、实际只有 search 用，knowpost 平行维护重复类型 |
| 纯别名/转发垫片在迁移完成后删除 | `knowpost/id.go` 曾是 pkg/idgen 的空转发层 |
| 消费失败的终点是死信表而不是一行 Warn | `outbox.DeadLetterRepository`，三个消费者统一注入 |
| 只增不减的集合必须有退出机制（惰性检查或巡检） | 大 V 名单曾只进不出，现 `IsCelebrity` 内建滞回降级 |
| context 传值用私有类型键，经最小公共包中转 | trace_id 曾用裸字符串键读 gin 私有存储，从未取到值 |
| 测试与被测代码同包同目录（集成测试用 `_test` 包后缀区分） | 曾有 `pkg/middleware/tests/` 孤儿子包 |
| 只有读取方、没有写入方的键空间是死代码，删除而非补写 | `liker_time:{...}` 从未被写入，回退路径为它逐人 GET 永远 miss |
| 被新表示取代的旧存储层要**连根**移除（Lua/常量/助手/测试），同一数据不允许两套表示并存 | SDS 早已全面 Hash 化，但二进制槽位 Lua、FieldSize 与大端助手仍在——只剩测试在测一个不存在的格式 |
| 配置参数要么真可配、要么不出现——不许传永远为 nil 的假参数 | feed 版本短缓存曾接一个恒为 nil 的 cfg，注释还声称「共用配置项」 |
| 模块边界（service 接口）返回 `error`，不返回具体错误类型指针 | auth 曾全线返回 `*errcode.AppError`：typed-nil 陷阱（`err != nil` 恒真）+ 全站唯一双轨；现统一 `error`，handler 出口 `httputil.ToAppError` 归一化 |
| 面向公网的分页参数必须同时有下界与**上界** | 公共 Feed 的 page 曾无上界，任意请求可驱动 MySQL 深 OFFSET 扫描；现 clamp 到 `maxPublicFeedPage=1000` |

## 面试一分钟版

> 这个项目沉淀了一组设计约定，每条背后都有真实踩过的坑：接口在消费侧按需声明（曾因 13 方法胖别名把测试桩撑到 60 行）；缓存只存共享视图、用户态读后叠加，并且这条不变量由 Tiered 组件的结构保证而不是靠纪律（曾因三处手写读穿流程中一处顺序写反，造成跨用户串号）；每模块一份键注册表，键属于谁 Lua 就放在谁那里（曾把别人模块的键格式复制进自己的脚本）；配置默认值单源（曾有靠注释维持一致的第二张数字表）；至少一次投递下，幂等操作先行、不幂等操作与去重标记同一原子单元（曾因先落标后计数，重投把事件永久丢掉）；动态列表一律复合游标分页（曾因排除式区间在并列时间戳的页边界丢条目）；以及——存储选型不能反向决定 API 语义，查询语义不匹配就为它建专用索引（点赞列表曾按 userID 排序，只因位图只能这么枚举）。
