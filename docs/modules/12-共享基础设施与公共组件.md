# 共享基础设施与公共组件

## 1. 模块定位

这部分包括：

1. `database`
2. `messaging`
3. `config`
4. `redislock`
5. `middleware`（Trace / Logger / CORS / Metrics / **RateLimit** / OptionalAuth 等横切能力）
6. 其他 `pkg` 层基础组件

它们不直接承载业务，但对整个项目的工程质量影响非常大。

## 2. 一句话介绍

这个项目的基础设施层坚持“共享资源统一工厂化、关键参数配置化、分布式锁可复用化、消息中间件策略化”的思路：MySQL 用 sqlx 保留 SQL 控制力，Redis 和 Kafka 连接由统一工厂创建，配置在启动期做默认值填充和校验，分布式锁则抽成独立组件供 `knowpost`、`counter`、`auth` 等模块复用。

## 3. 核心组件

## 3.1 database

`database.NewDB()` 做了几件关键事：

1. 根据配置构造 DSN
2. 建立 sqlx 连接
3. 启动时 `Ping`
4. 设置连接池参数：
   - `MaxOpenConns`
   - `MaxIdleConns`
   - `ConnMaxLifetime`

Redis client 也由统一工厂创建，连接池参数从配置读取。

## 3.2 messaging

Kafka 工厂根据 topic 类型设置不同保证级别：

1. outbox topic
   - 更高可靠性
   - `RequireAll`
   - 更多重试
2. counter topic
   - 也要求较高可靠性
   - 但整体策略略轻

Reader 则统一通过 consumer group 创建。

## 3.3 config

配置层不只是“读 yaml”，还负责：

1. 默认值填充
2. 启动期校验
3. 区分核心依赖和可选依赖

这个层次决定了很多问题是在“启动时暴露”还是“运行中爆炸”。

## 3.4 redislock

分布式锁组件具备：

1. `SET NX PX` 抢锁
2. token 标识归属
3. Lua 安全释放
4. Lua 安全续约
5. 手写 watchdog
6. `TryAcquire`
7. `AcquireWithRetry`

它被多个模块复用：

- `knowpost` 回源锁
- `counter` rebuild / repair 锁
- `auth` refresh 会话锁
- `relation` 缓存预热锁

```mermaid
sequenceDiagram
    participant S as Service
    participant L as redislock
    participant R as Redis

    S->>L: TryAcquire / AcquireWithRetry
    L->>R: SET key token NX PX
    alt 成功
        L-->>S: token
        S->>S: 临界区业务
        opt 长任务
            L->>R: Lua 续约 watchdog
        end
        S->>L: Release(token)
        L->>R: Lua 校验 token 后 DEL
    else 失败
        L-->>S: 未拿到锁
    end
```

## 3.4.5 internal/cache 组件族（教学深度拆解）

| 组件 | 职责 |
|---|---|
| `Tiered[T]` | L1→L2→锁回源的通用读穿编排（详见下文） |
| `Versions` | 「版本号编进缓存键」失效模式的读取端统一，自带进程内短缓存 + 写侧 Drop |
| `PrefixCache` | 共享 freecache 的键前缀隔离（自 knowpost 上收） |
| `HotKeyDetector` | 跨实例热点识别（`hotkey:active` 标记值即等级） |
| `RedisBloom` | 第三方 CF.* 适配层，存在性预判，fail-open |

### Tiered[T]：一个抽象的诞生过程

**问题**：同一套读穿舞步在 3+ 处手写，细节漂移直接制造了跨用户串号事故（一处在 enrich 后才写缓存）。
**解**：编排收进组件，业务只交五类"业务件"（键 / Loader / TTL 策略 / PreLoad / 锁参数）。

```mermaid
flowchart TD
    G["Get(key, loader)"] --> L1{L1 命中且解码成功?}
    L1 -->|是| RET1["返回 (v, HitL1)"]
    L1 -->|否| L2{L2 命中?}
    L2 -->|NULL 哨兵| EN["ErrNullCached"]
    L2 -->|JSON| BF["解码成功才回填 L1"] --> RET2["(v, HitL2)"]
    L2 -->|miss| PRE["PreLoad 钩子<br/>(如 Bloom 预判)"]
    PRE -->|拒绝| ERR[原样返回错误]
    PRE -->|放行| LK["抢锁 + double check L2"]
    LK --> LD["Loader 回源"]
    LD -->|"found=false"| NW["写 NULL 哨兵"] --> EN
    LD -->|err| ERR2["不写任何缓存, 透传"]
    LD -->|ok| WB["Encode → 写 L2 → 回填 L1"] --> RET3["(v, HitLoad)"]
```

**不变量（组件的灵魂）**：缓存写入全部发生在 `Get` 返回之前，内容只可能是 Loader 原始产物——
调用方在返回值上叠加用户态怎么改都污染不了缓存。"共享视图进缓存、用户态读后叠加"由结构保证。

**HitLevel 的用途**：调用方按命中级做差异化（详情场景：HitL2 才刷新计数——载荷计数可能陈旧；
HitL1 窗口极短、HitLoad 刚查过，均不刷）。

### Versions：版本号读取端

写侧 INCR 很简单，坑在读侧：版本号编码在缓存键里，"读 L1"必须先"知道版本号"——
没有本地短缓存时，**每次 L1 命中都要先付一次 Redis 往返**（详情与公共 Feed 都踩过）。

```mermaid
flowchart LR
    G[Get verKey] --> C{本地短缓存<br/>默认 2s}
    C -->|命中| R[版本号]
    C -->|miss| RD[Redis GET] --> WB[写回短缓存] --> R
    W[本实例写] --> I[INCR] --> D[Drop 本地] -.-> Z[自写自读立即切新键]
```

取舍：跨实例写入最多延迟 2s 切新键——远小于 L1 载荷自身 60s 的 TTL 窗口，
版本号的"即时性"本就不构成端到端强一致；用 2s 换掉每次读取一个 RTT 是净赚。

## 3.5 middleware / ratelimit（IP 滑动窗口限流）

`pkg/middleware/ratelimit.go` 提供按客户端 IP 的分布式限流，模型是 Redis ZSET 滑动窗口：

1. 每个 IP 一个 ZSET，**成员 = 一次请求**，**score = 该请求发生的毫秒时间戳**
2. `ZREMRANGEBYSCORE` 剔除窗口外的旧请求
3. `ZCARD` 得到窗口内请求数，与 `per_ip` 比较
4. 放行则 `ZADD` 记入本次请求，并 `PEXPIRE` 续期
5. 超限且配置了 `ban_duration_ms` 时，写入封禁名单 `ratelimit:ban:{ip}`

以上五步在**一个 Lua 脚本内原子完成**，不存在「查完再写」的竞态窗口。

### 两个容易写错、且写错就等于没限流的点

**一、score 必须取 Redis 服务端时间**

脚本内用 `redis.call('TIME')` 取时间，而不是从 Go 侧传入 `time.Now()`。多实例部署时各进程时钟存在偏差，用本地时间会让窗口边界在实例间抖动；以 Redis 为唯一时间源，窗口语义在所有实例上一致。

**二、成员必须逐请求唯一**

> ⚠️ 这是本组件历史上真实出过的缺陷，也是最值得记住的一条。

`ZADD` 对**已存在的 member 只更新 score，不新增元素**。早期实现把毫秒时间戳同时当作 score 和 member：

```lua
redis.call('ZADD', key, currentMs, currentMs)  -- ❌ score 和 member 都是 currentMs
```

于是同一毫秒内到达的 N 个请求全部落在同一个 member 上，互相覆盖，`ZCARD` 永远只记 1 次。结果是**突发流量可以完全绕过限流**——而突发流量恰恰是限流最需要拦住的场景。

现在的实现由 Go 侧生成唯一成员：

```
member = <进程启动时的随机前缀> + <进程内原子自增序号>
```

随机前缀隔开多实例的成员空间，原子自增保证同实例内不重复。ZSET 规模仍然有界：超过 `per_ip` 即拒绝，不再 `ZADD`，因此元素数最多为 `per_ip`。

回归测试 `TestRateLimiter_SameMillisecondBurst_IsCounted` 用紧凑循环制造同毫秒突发，断言放行数严格等于 `per_ip`。

### 其他行为约定

- 响应头 `X-RateLimit-Limit` / `X-RateLimit-Remaining` 由脚本返回的真实余量填充（早期实现恒为 `per_ip - 1`，是个无意义的常量）；被拒时额外返回 `Retry-After`。
- 客户端 IP 兜底解析使用 `net.SplitHostPort`。早期按 `":"` 切分，而 IPv6 地址本身含冒号，`[::1]:8080` 会被截成 `[`，导致所有 IPv6 客户端共用同一个限流桶、互相挤占配额。
- Redis 故障时 **fail-open**：记一条 Warn 后放行。限流是保护性组件，不应让它自身的可用性问题升级为整站不可用。

```mermaid
flowchart TD
    A[请求进入] --> B{在封禁名单?}
    B -->|是| Z[429 + Retry-After]
    B -->|否| C[Lua 原子执行]
    C --> C1[TIME 取服务端毫秒]
    C1 --> C2[ZREMRANGEBYSCORE 清窗口外]
    C2 --> C3[ZCARD 统计窗口内]
    C3 --> D{count >= per_ip?}
    D -->|是| E[PEXPIRE 续期] --> F[返回 0] --> G[按需写封禁名单] --> Z
    D -->|否| H[ZADD 唯一 member] --> I[PEXPIRE] --> J[返回 1 和真实余量]
    J --> K[写 X-RateLimit-* 头并放行]
    C -.Redis 故障.-> Y[记 Warn 后 fail-open 放行]
```

## 4. 设计亮点

## 4.1 不用 ORM，而是用 sqlx

这是一个很典型的后端工程取舍。

优点是：

1. SQL 完全可控
2. 更适合复杂查询优化
3. 没有 ORM 隐式行为

特别适合这个项目这种：

- 有不少列表查询
- 有事务 outbox
- 有多模块联表

的系统。

## 4.2 分布式锁抽成公共组件，而不是每个模块各写一套

这很重要，因为分布式锁最怕：

- 每个人各写一个版本
- 细节不一致
- 有人忘记 token 校验
- 有人没做安全释放

抽成 `pkg/redislock` 之后，锁语义可以统一，业务模块只关心“为什么要锁”，不用重复实现“怎么安全加锁”。

## 4.3 配置问题尽量前移到启动期

配置错误如果在运行中才暴露，排查成本很高。  
当前项目通过启动期校验，把很多错误前移到：

- 服务一启动就失败
- 或明确降级成可选能力不可用

这是一种很典型的工程质量思路。

## 5. 难点与边界

### 5.1 分布式锁的难点不是加锁，而是安全续约和安全释放

只会写 `SETNX` 还不够。  
真正要处理的是：

1. 锁是不是自己持有的
2. 续约时 token 是否仍匹配
3. 释放时是否误删别人的锁
4. 长耗时操作如何避免锁提前过期

这个项目的 redislock 组件把这些问题都考虑到了。

### 5.2 Kafka 配置不是一套参数打天下

不同 topic 可靠性要求不同。  
如果所有 writer 都用同样配置，可能会出现：

- 重要链路保护不够
- 非关键链路过度保守

当前项目按 topic 类型做了策略区分，这是正确方向。

### 5.3 启动期配置校验要有边界

不是所有配置缺失都该启动失败。  
关键在于：

- 核心依赖缺失 -> fail fast
- 可选能力缺失 -> degrade

## 6. 面试官高频问题

### Q1：为什么你这个项目不用 ORM？

**参考回答：**

因为这个项目的核心链路里有不少需要精确控制的 SQL，例如：

- 事务 outbox
- 关系列表查询
- feed 分页
- 搜索投影回查

我更看重对 SQL 的控制力和可解释性，所以用 sqlx 做轻量映射，而不是用 ORM 把查询隐藏掉。

### Q2：为什么要自己封一个 redislock？

**参考回答：**

因为多个模块都需要同一种锁语义。  
如果每个模块各写一套，会出现实现不一致、忘记 token 校验或看门狗逻辑不统一的问题。  
抽成公共组件之后，业务层只关心“为什么要锁”，而安全续约和安全释放逻辑可以统一复用。

### Q3：配置为什么要区分核心依赖和可选依赖？

**参考回答：**

因为不同组件对系统可用性的影响不同。  
MySQL、Redis 这种核心依赖缺失，系统就不该启动；  
搜索、LLM、OSS 这种增强能力缺失，系统仍然可以对外提供主站能力，只是对应接口降级。  
这是保证系统韧性的关键。

### Q4：为什么 Kafka writer 要按 topic 区分可靠性策略？

**参考回答：**

因为不同 topic 的业务价值不同。  
outbox 链路是很多派生系统的源头，可靠性要求更高；  
counter 事件也重要，但策略可以略轻一些。  
我不想用一套统一配置去粗暴覆盖所有链路。

## 7. 场景题

### 场景题 1：如果数据库连接经常被打满，你会先看哪里？

**推荐回答：**

我会先从三层排查：

1. 连接池配置是否合理
2. 是否有慢 SQL 或事务过长
3. 是否有缓存策略失效导致回源放大

也就是说，这不一定只是 DB 参数问题，往往和上层读写放大一起有关。

### 场景题 2：如果某个分布式锁持有时间明显超过预期，你会怎么处理？

**推荐回答：**

我会先区分：

1. 是业务逻辑确实变慢了
2. 还是续约策略不合理

再看：

- 锁粒度是否过大
- 是否可以拆临界区
- 是否应该把长任务改成异步

不能只靠把 TTL 调大去掩盖问题。

## 8. 最容易讲错的地方

不要把基础设施层说成“只是工具类”。  
中高级面试官很在意的往往恰恰是这些公共能力，因为它们决定了：

- 项目是否能稳定运行
- 复杂度是否可控
- 业务模块是否能复用统一约束

## B4. Redis 分布式锁生命周期

```mermaid
sequenceDiagram
    participant Caller as 调用方
    participant Lock as redislock
    participant Redis as Redis
    participant Dog as Watchdog

    Caller->>Lock: TryAcquire / AcquireWithRetry
    Lock->>Redis: SET key token NX PX ttl
    Redis-->>Lock: locked
    Lock->>Dog: 启动看门狗
    Dog->>Redis: Lua 校验 token 后 PEXPIRE

    Lock->>Dog: stop
    Lock->>Redis: Lua 校验 token 后 DEL
```

关键点：释放和续约都必须校验 token，不能误删或续约别人的锁。

## B10. 共享基础设施 2 分钟口述

> 共享基础设施层解决的是跨模块的一致工程约束。配置层负责 YAML 加载、默认值和启动校验；database 层负责 MySQL、Redis 连接池和迁移；redislock 把 SET NX PX、token、Lua 安全释放和看门狗续约收成一个公共组件；错误码和 response 保证所有接口返回结构一致；Kafka reader/writer、metrics、health check 统一接入 App 生命周期。这里的重点不是工具函数多，而是让业务模块不用重复处理连接池、超时、锁、错误和生命周期这些容易出问题的底层细节。

# 附录C：函数级源码走读（internal/cache 与 ratelimit）

## C1. `tiered.go` — Tiered[T]

#### `Get(ctx, key, load Loader[T]) (T, HitLevel, error)`
- **逐步**：
  1. L1：`L1.Get` 命中且 `Decode` 成功 → `(v, HitL1)`；解码失败按 miss（旧布局残留不回传）；
  2. `getL2`：命中 → `(v, HitL2)`；哨兵 → `ErrNullCached`；
  3. `PreLoad` 钩子（如 Bloom）：返回 err 即中止原样上抛；
  4. LockKey 为空 → 直接 `loadAndFill`；否则 `cacheutil.CacheReadThrough`：checkCache=再跑一次 `getL2`（锁内 double check），missHandler=`loadAndFill`；
  5. 命中级经 `hitResult` 结构穿透锁层带回。
- **不变量**：返回前缓存已全部写完，内容只可能是 Loader 原始产物——调用方叠用户态污染不了缓存。

#### `getL2(ctx, key) (T, bool, error)`
- **逐步**：Redis 为 nil / GET 失败 / 空串 → miss（**Redis 故障按 miss，缓存层不阻断读路径**）；等于 NullSentinel → `ErrNullCached`；Decode 失败 → miss 回源重建；成功 → `fillL1` 回填**原始字节**再返回。

#### `loadAndFill(ctx, key, load) (T, error)`
- **逐步**：Loader err → 原样上抛**不写任何缓存**；found=false → 写 NullSentinel（NullTTL()）→ `ErrNullCached`；成功 → Encode（失败仅记 Warn，本次结果照常返回）→ 写 L2（L2TTL() 每次现取，可带 jitter/热点延长）→ `fillL1`。

#### `fillL1(key, raw)` / `logWarn`
- freecache 对超容量 1/1024 的单条会拒写——**必须记 Warn**，静默会让该键永远不走 L1 且无人知晓。

## C2. `version.go` — Versions

#### `Get(ctx, redisKey) int64`
- **逐步**：Local 启用（Local!=nil 且 TTL>0）→ 先查本地（`{LocalPrefix}{redisKey}`），ParseInt 成功即返回；miss → Redis GET（nil 客户端/键缺失/<=0 → Default）→ 写回本地（失败忽略，下次回落 Redis）。

#### `Drop(redisKey)`
- 写侧递增版本号后**必须**调用：作废本实例短缓存，保证自写自读立即切新键（跨实例靠 TTL 自然过期，窗口远小于 L1 载荷 TTL）。

## C3. `prefix_cache.go` — PrefixCache

| 函数 | 要点 |
|---|---|
| `Get/Set/Del` | 透传 freecache，键前缀隔离共享实例的多用途 |
| `prefixed(key)` | 每次 `make` 新切片拼接。**刻意不用 sync.Pool**：历史版本只 Get 不 Put，比直接分配还慢（实测 288B/3allocs → 56B/2allocs）；返回值生命周期跨出函数边界，归还时机无法安全判定 |
| `SetOrWarn(logger,...)` | Set 失败记 Warn（含 valueBytes）——超限条目永久不进 L1 必须可见；logger nil 安全 |

## C4. `ratelimit.go` — RateLimiter（pkg/middleware）

| 函数 | 逐步/要点 |
|---|---|
| `NewRateLimiter(rdb,cfg,logger)` | logger nil → Nop；未启用或 rdb nil → Middleware 退化为直通 |
| `Middleware()` | ①封禁名单 EXISTS；②`rateLimitScript` 单段 Lua：服务端 TIME 取毫秒 → ZREMRANGEBYSCORE 清窗口外 → ZCARD 判限 → 放行则 ZADD **唯一 member** + PEXPIRE，返回 {allowed, remaining}；③超限按需写封禁键 + 429（带 Retry-After）；④Redis 故障 fail-open 放行记 Warn |
| `nextRateLimitMember()` | 进程随机前缀 + 原子自增序号——ZADD 对相同 member 只更新 score，member 不唯一时同毫秒突发折叠成 1 次计数，限流完全失效（历史真实缺陷） |
| `clientIP(c)` | gin ClientIP 为空时 `net.SplitHostPort` 兜底——按":"切分会把 IPv6 `[::1]:8080` 截成 `[`，全部 IPv6 客户端共用一个桶 |
| `reject(c)` / `ban(ctx,...)` | 统一 429 响应头（Limit/Remaining/Retry-After）；封禁时长可配 |
